# The Bulwark corpus

A library that ships regexes without measurements is asking to be trusted on
vibes. This directory is the answer to "how well does it actually work?" — a
labeled, language-agnostic corpus that all three implementations grade
themselves against, and that CI defends against regression.

```bash
python3 tools/corpus.py            # validate + summarize
python3 tools/bench.py             # precision / recall / F1 / FPR, per class and language
python3 tools/bench.py --gate      # fail if we regressed against corpus/BASELINE.json
python3 tools/conformance.py       # prove Python, TypeScript and Swift agree
```

## Layout

```
corpus/
├── parts/           the shards, one JSONL file per author area
├── corpus.jsonl     generated: every shard merged, what the TS/Swift drivers read
├── BASELINE.json    generated: the numbers CI compares against
└── README.md
```

`corpus.jsonl` and `BASELINE.json` are regenerated by the tools; edit the shards.

## Format

One JSON object per line. Newlines inside `text` are escaped; invisible and
control characters are written as `\uXXXX` escapes so the files stay reviewable
in a normal editor — a corpus you cannot read is a corpus you cannot trust.

| field | on | meaning |
|---|---|---|
| `id` | all | unique, `<prefix>-NNN`, prefix owned by one shard |
| `text` | all | the document as it would arrive from an untrusted source |
| `label` | all | `attack` or `benign` |
| `expect_injected` | all | **ground truth**: should a correct detector flag this? |
| `notes` | all | one sentence on why this case exists |
| `class` | attacks | `instruction_override`, `role_injection`, `prompt_leak`, `exfiltration`, `jailbreak`, `tool_injection`, `boundary_breakout`, `encoding`, `summary_poisoning`, `agentic` |
| `technique` | attacks | the specific trick, e.g. `polite-indirect`, `base64-nested` |
| `genre` | benign | e.g. `security-writing`, `api-docs`, `changelog`, `recipe` |
| `language` | all | BCP-47-ish code of the document |
| `hard` | optional | a genuinely borderline case; reported separately, never gates CI |

## The one rule that matters

**`expect_injected` is ground truth, not a prediction.** It records what a
careful security engineer would say about the document — never what Bulwark
currently says about it.

That distinction is the whole point. A corpus tuned to the current
implementation measures nothing: it will show 100% forever and tell you nothing
about the next attack. A corpus written independently of the implementation
produces a **backlog** — every attack in the `misses` list is a real weakness
with a reproducible test case attached, and every entry in `false_positives` is
a real document Bulwark would wrongly flag for a real user.

So: when a benchmark run disagrees with the corpus, fix the detector. Change a
label only when the label is genuinely wrong about the document, and say why in
`notes`.

## Adding cases

New signatures and red-team cases are the most useful contributions this project
can receive. To add some:

1. Pick the right shard, or add a new one with an unused id prefix.
2. Write realistic documents. Most entries should embed the payload in a page
   someone would actually want summarized — position it at the start, the middle
   and the end across your cases, because detectors behave differently at each.
   A bare one-line payload is a unit test, not a corpus case; keep those to a
   minority.
3. Do not tune against the detector. Write the case, then run the benchmark.
4. `python3 tools/corpus.py` must pass — it rejects duplicate ids, duplicate
   text, contradictory labels and unknown classes.
5. If your case exposes a miss, that is a *successful* contribution. Open the PR
   with the case even if you have no fix; the failing entry is the bug report.

Benign cases are worth as much as attacks. False positives are how a security
tool gets switched off, and the hardest benign documents — security writing, LLM
API docs, changelogs, recipes, legal boilerplate — are exactly the ones people
most want summarized. There are deliberately a lot of those in
`benign-adversarial.jsonl`.

## What the numbers mean

The corpus is **adversarially weighted on purpose**. It is not a sample of what
arrives in an average request; it is stacked with the attacks most likely to
evade a regex-based detector, because those are the ones worth knowing about.
Read recall as "share of hard, realistic attacks caught", not "share of traffic
caught" — the latter would be a much larger and much less useful number.

The false-positive rate is the honest one, and it should be read at face value.
